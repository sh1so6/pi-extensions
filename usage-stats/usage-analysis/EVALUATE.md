# キャッシュ運用の評価手順 (EVALUATE)

対象: `cache-ttl-main` (メインだけ 1h TTL) と `context-relay` (閾値 200k の入力時トリガ / 期限前トリガ)。
目的: 「この運用で実際に安くなっているか」と「relay の閾値は妥当か」を、同じ手順で繰り返し確認する。

## 実行

```
node <package dir>/usage-analysis/cache-eval.mjs --since 2026-11-18
node <package dir>/usage-analysis/cache-eval.mjs            # 全期間 (基準との比較用)
```

`--since` に評価区間の開始日を渡す。出力は 3 節。ログは `~/.pi/agent/sessions` (依存なし、node のみ)。

| 節 | 見るもの |
|---|---|
| 1. シナリオ比較 | actual / 5m(ウォーマー無し) / 5m+idle warm / 1h の入力側 $ (main・sub 別) |
| 2. prefix 帯別 | 帯ごとの 1 ターン単価と、200k 超がコストに占める割合 |
| 3. compaction 前後 | relay / 標準 compaction の前 P と後 S (実測)、分岐ターン数 20S/(P-S) |

## 前提 (計算の置き方)

- 倍率: 5 分書込み 1.25 / 1h 書込み 2 / 読込み 0.1。単価はログの cacheRead 単価 ×10。
- 入力側コストのみ (出力は除外)。反事実の再計算なので、再現値は実際の合計と約 2 割ずれる。見るのはシナリオ間の**差**。
- 反事実の hit 判定は、直前リクエストの終了から次の開始までの間隔で決める (5m=5分以内、1h=60分以内、idle warm=35分以内)。
- Claude サブスクでは課金は枠の消費。金額の比率がそのまま当てはまるかは未確認。
- 分岐ターン数 = 20S/(P-S) は、リセットの書込み (2S) を、毎ターンの読込み減 0.1(P-S) で回収するまでの数。relay の要約呼び出しと、失った文脈の再読込みは含まない (実際はもう少し長い)。
- 手動 /new は session 履歴に目印がないため、この手順では扱わない (relay と標準 compaction だけ)。

## 基準値 (2026-11-04 時点、全期間)

| 項目 | 値 |
|---|---|
| main 1h TTL (反事実) | $870 (実績 $1,142、idle warm $911、5m のみ $1,221) |
| main cache miss | 実績 1,444/20,346 → 1h なら 472 |
| sub | 5m のまま $1,787 (1h にすると $1,957 で約 10% 高い) |
| 200k 超のターン | 全体の約 27% で、コストの約 52% |
| 1 ターン単価 | 75k 付近 約 $0.04 → 250k 付近 約 $0.14 (約 4.5 倍) |
| relay 前 P / 後 S (中央値) | 147k → 61k (n=29)。分岐 約 14 ターン |
| 標準 compaction 前 P / 後 S | 383k → 63k (n=15)。分岐 約 4 ターン |
| 新規セッション初回の prefix | 約 21k (固定分。S の下限の目安) |
| ウォーマー | 全 1,807 件が cacheRead のみ (cacheWrite は 0 件)、合計 $56.5 |

relay 設定: `~/.pi/agent/context-relay.json` の入力時トリガ閾値 200k。Pi の `cacheWarming` は既定の `streaming` のまま。

## 判断基準 (2 週間後)

- **1h が効いているか**: main の actual が 1h シナリオに近づき、miss 率が下がっていれば OK。`cacheWrite1h > 0` のターンが十分あること (`/cache-ttl` でも確認できる)。
- **relay の閾値 (200k)**:
  - 節 2 で 200k 超のコスト占有率が下がっていれば効いている。
  - 節 3 の relay の S が 61k より大きく増えていたら、ノートや保持範囲が膨らんでいる。分岐ターンが 20 を超えるなら、閾値を下げるかノートを薄くする。
  - 標準 compaction の件数が増えていたら、relay が間に合っていない。閾値を下げる。
- **sub**: 1h のほうが安く見えるようになっていたら、サブの使い方 (長命化) が変わっている。`cache-ttl-main` の対象を見直す。
- 差が 5% 未満ならデータ不足として扱い、期間を延ばして再評価する。

結果は、このファイル末尾の「評価履歴」に日付つきで追記する。
